# Гидрация

Гидрация — клиентская инициализация поверх уже отправленной сервером HTML-разметки. Вместо полного клиентского рендера `hydrate` забирает существующие серверные узлы, привязывает к ним реактивные эффекты и оставляет разметку нетронутой, пока резолвятся асинхронные ViewModel. Прелоадеры при этом не показываются. Используется после SSR-рендера, который выполняет `renderToString` из `@ivlev-dev/silent-server` и возвращает `{ html, head }`.

Минимальный сценарий:

```ts
import { hydrate } from "@ivlev-dev/silent-core";
import { App } from "./app";

const handle = await hydrate("#app", App, {
  props: { title: "Привет" },
  onMismatch: (error) => console.warn(error.message),
});

// handle.ready — промис готовности, handle.dispose() — демонтаж
```

На сервере разметка рендерится через `renderToString`:

```ts
import { renderToString } from "@ivlev-dev/silent-server";
import { App } from "./app";

const { html, head } = await renderToString(App, { props: { title: "Привет" } });
const page = `<!doctype html><html><head>${head}</head><body><div id="app">${html}</div></body></html>`;
```

## Как работает адоптация

Гидрация выполняется по границам, которые `hydrate` ставит вокруг содержимого `target`. В режиме адоптации рендер идёт не «с нуля», а в режиме претензии: каждый `template` и `templateHoles` сверяет форму следующего серверного узла и возвращает тот же узел, а не клон.

Окна (см. `HydrationWindow` в `packages/core/src/hydration.ts`) описывают диапазон, из которого берутся серверные узлы:

- `start` — начальный узел диапазона (служебный комментарий).
- `end` — конечный узел диапазона.
- `cursor` — указатель на следующий узел, который должен быть принят. Приём узла (`claimNext`) сдвигает `cursor` на `nextSibling`.

`renderAdopted` создаёт окно для view с `cursor = start.nextSibling` и проверяет после рендера, что `cursor === end`: иначе это несовпадение. Вложенные окна вставляются через `withWindow`.

Маркеры, используемые при адоптации:

- `silent-view` / `silent-view-end` — границы view-компонента; сервер сериализует пару, чтобы клиент нашёл свою область.
- `silent-item` / `silent-end` — якоря keyed-списков (`For`, `Index`).
- `silent-hole-N` — комментарии-заполнители динамического контента внутри `templateHoles`.
- `data-silent-a-N` — атрибуты-маркеры элементов с динамическими атрибутами. При гидрации они снимаются, а значения применяются заново.

Дополнительно используются регионы `silent-insert` / `silent-insert-end`: сервер создаёт их вокруг значения `insert`, а при гидратации первый проход в регионе ничего не вставляет — примитивы обновляют существующий текстовый узел, компоненты и шаблоны адоптируют свои узлы.

Управляющие конструкции (`Show`, `Switch`/`Match`, `Suspense`, `lazy`, `fragment`, `ErrorBoundary`) находят собственные якоря (`silent-show`, `silent-switch`, `silent-suspense`, `silent-fragment`, `silent-error`) и продолжают обычную реконсиляцию на последующих обновлениях. Ветки `Match` служебные: в DOM они не попадают и якорей не оставляют.

## Требования к разметке

- Разметка должна строиться через `template()`/`templateHoles()`. Произвольный DOM, собранный вручную внутри синхронного компонента, не адоптируется.
- На сервере и клиенте должен рендериться один и тот же компонент с одинаковыми `props` и одинаковыми условиями (ветви `Show`/`Switch`, состояния списков `For`/`Index`).
- Имя и порядок атрибутов-маркеров (`data-silent-a-N`) должны совпадать: они нумеруются компилятором; ручная перетасовка ломает адоптацию.
- Текстовые узлы должны совпадать побайтово: лишние пробелы, переводы строк и изменения в тексте считаются несовпадением.
- `<title>` должен быть прямым потомком корневого элемента шаблона view (вложенные глубже вызывают откат к клиентскому рендеру).
- `lazy` адоптирует содержимое после загрузки модуля; до этого остаётся серверная разметка.

## Правила для компонентов

### `For` и `Index`

- Сервер рендерит элементы списка, разделяя их маркерами `silent-item`, и завершает список маркером `silent-end`.
- Клиент забирает элементы по порядку и продолжает keyed-реконсиляцию на обновлениях; существующие узлы переиспользуются.
- Пустой список адоптирует свой `fallback`, если он был отрендерен сервером.
- Новые элементы после гидрации создаются как обычно (как при монтировании).

### `Show`

- Адоптируется та ветка, которая была отрендерена сервером (`children` или `fallback`).
- При последующем переключении ветка заменяется стандартным механизмом; узлы второй ветки создаются заново.

### `Switch` и `Match`

- Адоптируется активная на момент серверного рендера ветка `Match`.
- Маркер `silent-switch` остаётся в DOM; остальные ветки не присутствуют в серверной разметке.

### `Suspense`

- Сервер дожидается `ready` всех вложенных view (включая `lazy`, через `trackAsyncWork`) и сериализует их содержимое.
- При гидратации прелоадеры вложенных view не показываются; серверная разметка остаётся видимой, пока резолвится VM, затем view адоптируется.

### `lazy`

- До завершения импорта модуля серверная разметка сохраняется. После загрузки модуля его содержимое адоптируется.

### `fragment`

- Шаблон с несколькими корневыми узлами: корни забираются по порядку.
- Отложенные узлы (вынесенные маркерами) возвращаются на место через `settleNodes`.

### `ErrorBoundary`

- Адоптируется ветка, которая была отрендерена сервером (`children` или `fallback`); маркер `silent-error` служит якорем.

## Метаданные

`<title>`, `<meta>` и `<link>` не входят в `html` результата SSR — они выносятся в `head`:

- На сервере `setMetadataCollector` собирает `<title>`, `<meta>` и `<link>` из дерева; результат попадает в `RenderResult.head`.
- На клиенте заголовок создаётся заново и занимает `document.head`; текст обновляется реактивно.
- `<meta>` и `<link>` тоже выносятся в `head`: добавляются при монтировании и удаляются при размонтировании; существующие элементы `head` из `index.html` не трогаются.
- При размонтировании view заголовок удаляется, предыдущий (например, статический `<title>` из `index.html`) восстанавливается.
- Несколько одновременных заголовков не дедуплицируются — все попадают в `head`; рендерите один `<title>`.
- `<title>` внутри `<svg>`, а также `<title>`, `<meta>` и `<link>` с атрибутом `itemprop` не выносятся.
- Содержимое заголовка должно быть текстом: компилятор сворачивает статические и динамические части в один `textContent`-бондинг.
- `<title>` должен быть прямым потомком корневого элемента шаблона view.

## Ошибки

При несовпадении формы узла бросается `HydrationMismatchError`. Ближайший view отказывается от адоптации и рендерится клиентски; ошибка передаётся в `options.onMismatch`.

```ts
import { HydrationMismatchError } from "@ivlev-dev/silent-core";
import { hydrate } from "@ivlev-dev/silent-core";

const mismatches: HydrationMismatchError[] = [];
await hydrate("#app", App, {
  props: { title: "Привет" },
  onMismatch: (error) => {
    mismatches.push(error);
    console.warn(error.message);
  },
});
```

Если `onMismatch` не задан, по умолчанию в консоль выводится предупреждение `[silent] гидрация: <message>`. При несовпадении `hydrate` выполняет откат: строит свежий рендер без адоптации и заменяет содержимое `target` через `replaceChildren`. Порядок узлов и эффекты при этом совпадают с обычным `mount`.

Ограничения адоптации, ведущие к откату:

- значения должны создаваться через `template()`/`templateHoles()`;
- `<title>` должен быть прямым потомком корневого элемента шаблона view;
- `lazy` адоптирует содержимое только после загрузки модуля.

## Отладка

Как найти несовпадение:

1. Задайте `onMismatch` с логированием: сохраняйте `HydrationMismatchError` и выводите `error.message` и стек.
2. Сравните серверный HTML (из `renderToString`) с клиентским деревом: сообщение об ошибке указывает, какой узел не совпал (`view не совпал с серверной разметкой`, `не найден закрывающий маркер view`, `не найден конец региона вставки` и т.п.).
3. Проверьте, что серверный и клиентский рендер используют одинаковый компонент, одинаковые `props` и одинаковые условия.
4. Убедитесь, что разметка собрана только через `template()`/`templateHoles()`, а динамические атрибуты помечены `data-silent-a-N`.
5. Пройдитесь по текстовым узлам: любые лишние пробелы, переводы строк и несовпадающие тексты ломают адоптацию.

Типичные причины:

- другой порядок узлов между сервером и клиентом;
- лишние пробелы и переводы строк в текстовых узлах;
- ручной DOM, созданный вне `template()`/`templateHoles()`;
- несовпадение ветвей `Show`/`Switch` или состава списка `For`/`Index`;
- `<title>` вложен не в корневой элемент шаблона view;
- отсутствие или неверная нумерация `data-silent-a-N`.

## Ограничения

- Гидрация адоптирует только разметку, созданную через `template()`/`templateHoles()`; ручной DOM не адоптируется.
- Прогрессивный стриминг не поддерживается: `renderToStream` отдаёт уже готовое тело чанками; серверный мини-DOM не реализует события.
- Для SSR-сборки Vite рантайм должен оставаться внешним: добавьте все `@ivlev-dev/silent-*` в `ssr.external`, иначе приложение и `renderToString` получат разные модульные экземпляры.
- Пакет ESM-only, требуется Node.js 22+.
- `renderToString` сериализует вызовы через очередь, так как DOM-глобалы общие на процесс.
