# План производительности

Замеры ниже в разделе «Текущее состояние» — исторические (`0.7.1`); на текущем `main` они не воспроизводятся (см. «M3. Гидрация», запись про регрессию 0.7.5). Актуальные числа: Chromium 16.8–17.0k ops/s (0.58× Solid, p50 0.045 мс), jsdom 1 468–1 477 ops/s (0.62×), стартовый JS mount-only 35.0 KB / 11.9 KB gzip, SSR `renderToString` 84 323 ops/s (0.71× Solid). A/B в одном Chromium-процессе (текущий `main` против 0.7.5 с фиксом `getReady`): ratio среднего 0.92 (текущий быстрее), медианы 1.125 — в пределах одного тика таймера 5 µs, то есть фактически паритет в сценарии 20 строк.

Текущее состояние (`0.7.1`): `renderToString` **113 022 ops/s** на скомпилированном приложении с `For` (0.93–1.00× от Solid в соседних прогонах), гидрация **1 510 ops/s** в jsdom (0.66×) и **23 641 ops/s** в Chromium (0.89×, p50 0.035 мс; на загруженной машине 0.78–0.91×), на одном изолированном vCPU — 0.53–0.80×. Сэмплированные аллокации гидрации — 4941.7 KB (метрика в `bench:guard`). Warm `pnpm build` — десятки миллисекунд, Vite build приложения Silent 57/37 мс против Solid 124/32. Стартовый JS **27.7 KB / 9.4 KB gzip** с `view: false` и 31.5 KB / 10.9 KB gzip в default-режиме с lazy view-чанком против 12.6 KB у Solid. Бенчмарки ограничены четырьмя CPU через `scripts/bench-cpus.mjs` (или одним изолированным ядром в `bench:vm`) и измеряют код после компилятора, а не ручные вызовы `templateHoles`/`insert`.

История шагов: 8 746 ops/s (0.32x) → дескриптор 9 772 → текстовые дыры 10 209 → гибридная адопция 11 820–12 104 → owner/реактивность 13 762–15 151 → scoped-эффект и plan-first 14 228 → fast path регионов 16 269–16 863 → массивы зависимостей 17 590 → пропуск статических выражений 18 293 → адопция списка без эффекта 18 490 → ленивые узлы элементов списка 22 531 → пул пробных проходов 23 456 → ключи плана адоптации и классы состояния строки 23 641. После 0.7.5 замеры просели (см. запись про регрессию в M3); текущая волна: 9 900–10 400 → 11 100–11 700 → ~13 100. Наклон `ROWS=1`→`ROWS=20`: построчная часть сравнялась с Solid, остаток разрыва — фиксированные накладные.

## M2. Строковый SSR

- [x] SSR-режим компилятора: JSX → строковая конкатенация без `templateHoles`/`insert` и мини-DOM. Опция `ssr: true` (Vite-плагин включает её для SSR-сборок и `vite.ssrLoadModule`); статические части выносятся в массив `_tmpl$N`, кодогенерация — прямая конкатенация `_$ssrRaw(... + _$ssrValue(expr, bare) + ...)` без массива значений. `ssrValue` экранирует и сохраняет регионы вставки, маркеры `silent-hole-*`/`data-silent-a-*` остаются, разметка совпадает байт-в-байт с шаблонным путём, гидрация не меняется. Результат — лёгкий `RawText` вместо `RawNode`; серверные `For`/`Index` собирают строку напрямую (без `RawNode` и hole-объектов на список). Для динамических атрибутов, `style`/spread, `dangerouslySetInnerHTML`, RCDATA-значений и metadata-тегов — откат на `templateHoles`. `renderToString` 105 000–115 000 ops/s, 0.93–1.15× от Solid.
- [x] Статические шаблоны, `Show`/`Switch`/`Index`/`ErrorBoundary` и серверный `For` без мини-DOM: `createTemplate` отдаёт `RawNode` и при нуле дыр, `Show`/`Switch` сразу разрешают ветку и дописывают якорь, `ErrorBoundary` вызывает `children` синхронно с сохранением `onError`-отката, `For`/`Index` вынесены в отдельные серверные функции без замыканий реконсиляции. `For`/`Index` переиспользуют строки маркеров и один аксессор индекса, у узлов мини-DOM список детей аллоцируется лениво, восстановление глобалов — прямыми присваиваниями. Разметка собирается конкатенацией строк в `RawNode.render` вместо `parts.join`, вложенные `RawNode` вставляются одной строкой. В A/B-прогоне SSR относительно Solid: 0.60 → 0.70–0.76.
- [x] Строковые дыры для динамических атрибутов (`class`, `style`, spread). `createTemplate` отдаёт `RawAttr`, который пересобирает строку атрибутов из `Map`/`Set` и дописывает их после статических (как мини-DOM), сохраняя маркер `data-silent-a-*` для гидрации; для `textarea`/`title` `value`/`textContent` уходят в содержимое элемента экранированным текстом. Шаблоны с атрибутами больше не откатываются на разбор мини-DOM.
- [ ] Внутренний `ssr-runtime` с `escape`/`escapeAttr`/`serializeValue` без объектов-узлов (рефакторинг ради чистоты: на скорость не влияет, `serializeValue` уже не создаёт узлов).
- [x] `renderToString` без `installDomGlobals` — замерено и отклонено: установка/снятие девяти глобалов стоит меньше шума (112 653/114 187 против 111 651/113 022 ops/s).
- [x] Скомпилированный SSR-бенчмарк Silent vs Solid: `bench:ssr` гоняет `silent-app-ssr.mjs` и `solid-app.tsx`.
- [x] Цель: паритет с Solid на простых шаблонах, обгон на списках/тексте. На скомпилированном приложении с `For` — 0.93–1.15× (среднее ~1.0).

## M3. Гидрация

- [x] Plan-based adoption для шаблонов без метаданных.
- [x] Курсорный `shapeMatches` без массивов и `NamedNodeMap`-прокси.
- [x] Компиляторные гидрационные ключи вместо структурного поиска: в записи `holes`/`attrs` плана добавлено готовое имя маркера (`key: "silent-hole-N"` / `"data-silent-a-N"`), адоптация сравнивает `Comment.data` и `hasAttribute` без `startsWith` и разбора числа; при отсутствии `key` (рантайм-планы) — прежний путь через `markerIndex`. Цена — ~0.4 KB стартового JS на шаблонах приложения.
- [x] Эффект-владелец вместо `EffectNode`: `createEffectUnlessStatic` без собственных зависимостей, но с вложенными эффектами/cleanup'ами создаёт лёгкий `OwnerNode` и `disposeOwner` вместо `createEffectNode`, поэтому строка списка и `insertHydrated` не платят за узел графа с `deps`/`state`.
- [x] Быстрые пути обхода: `findInsertWindow` для пустого региона (`INSERT_START` рядом с `INSERT_END`), `insertHydrated` без вызова `findInsertWindow` при пустом регионе, `pickSignificantChild` возвращает комментарий-дыру при `counts === 1`.
- [x] Гидрация без материализации клиентского дерева для шаблонов с дескриптором: статические узлы адоптируются, эффекты привязываются к серверным узлам; metadata-шаблоны по-прежнему идут через клон.
- [ ] Следующий резерв — фиксированная часть (~16 µs против ~11 у Solid): обход `significantChildren*` по путям плана, границы гидрации (2 комментария + 2 вставки/удаления), `toOwner` и реестр слушателей на элемент. Строковая часть разрыва уже закрыта.
- [ ] Инкрементальная/ленивая гидрация статических поддеревьев.
- [ ] Пропуск полной проверки формы для доверенной SSR-разметки с ключами (plan-path валидирует только маркеры, `shapeMatches` остаётся у fallback).
- [x] Бенчмарк гидрации в реальном Chromium (`pnpm bench:browser`): Silent 8 746 vs Solid 27 372 ops/s.
- [x] Бенчмарк отделяет подготовку от гидрации: таймер уже не включает `innerHTML`, добавлен столбец «разбор» (контейнер + `innerHTML`). По p50: гидрация silent 0.205 ms против solid 0.065 ms (3.2×), разбор разметки 0.09 против 0.05 ms (в ops/s не входит).
- [x] Замеры стоимости: проверка атрибутов в `shapeMatches` на скорость не влияет (jsdom 1 308 против 1 368, Chromium 8 429 против 8 746 — шум), `cloneNode(true)` для снимка разметки дороже `innerHTML` (7 999 против 9 299).
- [x] Не читать `innerHTML` для отката, когда откат невозможен (сборка без ViewModel или view-рантайм уже загружен).
- [x] Этап A: `settle()` без двойного `whenIdle`/`flushSync` и удаление региона одним `Range.deleteContents()` вместо поштучных `removeChild`. В бенчмарке изменения не видны (8 549 и 7 940 против 8 233–9 090 до, p50 0.095 без изменений) — значит микро-накладные расходы не главное.
- [x] Починить подписку при гидрации, если текст передан геттером сигнала (`{count}` вместо `{count()}`).
- [x] Компиляторный дескриптор адопции: `_$templateHoles(html, plan)` получает пути дыр и атрибутов, `counts` и `strips`; в гидрации не парсится `<template>` и не вызывается `shapeMatches`, найденные по путям узлы валидируются по маркерам, при расхождении — `mismatch` и откат. Chromium 8 746 → 9 772 ops/s (0.32x → 0.38x к Solid), стартовый JS 23.2 → 24.8 KB (8.3 → 8.6 KB gzip). Планы не генерируются для metadata-шаблонов и тегов с неявной перестройкой парсером (`table`/`select`/`p`/`a`/`form` и т.п.) — они идут старым структурным путём.
- [x] Текстовые дыры без insert-регионов: примитив в позиции без статического текста сервер выводит текстом, клиент привязывает эффект к существующему `Text`, а при смене типа на узел создаёт регион. Адоптация находит дыры и атрибуты одним обходом по маркерам (`collectPartsMany`), поэтому текстовые значения не сдвигают пути. На текстовую дыру −2 служебных узла; Chromium 9 222–10 213 ops/s (p50 0.075–0.080 мс), стартовый JS 25.0 KB / 8.7 KB gzip.
- [x] Регионы обновляются без пересборки: `writeRegion` кэширует состояние региона по стартовому комментарию, переиспользует узлы по идентичности и обновляет `Text` на месте; `clearView` больше не диспозит узлы региона повторно, `Range.deleteContents` удаляет остатки одним вызовом. `For` уже использует keyed-реконсиляцию без пересоздания узлов — тесты на перестановки и вставки это фиксируют.
- [x] Гибридная адопция: быстрый путь по путям плана (hole принимает `Text` перед маркером, attr проверяется по `data-silent-a-i`), маркерный обход — только fallback при разъехавшихся путях. GC 20% → 14.6%, Chromium 10 209 → 11 820–12 104 ops/s, p50 0.075 → 0.065 мс.
- [x] Ленивые аллокации: `For` не создаёт `DocumentFragment`-контейнер и типизированные буферы до первого обновления, `createViewResult` создаёт фрагмент только в non-hydration.
- [x] Лёгкие owner/effect: `children`/`cleanups` у owner создаются по требованию, у effect убран неиспользуемый `observers`-Set, `deps`/`depVersions` и `nextDeps`/`nextDepVersions` аллоцируются только при первом чтении зависимости. GC 20% → 14–16%, Chromium 12 104 → 13 762–15 151 ops/s, p50 0.065 → 0.050–0.055 мс.
- [x] Проверки маркеров через `nodeType` вместо `instanceof Comment`; в `For` маркер элемента проверяется только у комментариев.
- [x] Гидрационная адоптация перенесена из стартового `dom.ts` в ленивый `dom-hydration`: стартовый JS 26.2 → 25.5 KB (8.9 → 8.8 KB gzip) без замедления в пределах шума.
- [x] План как первый проход адоптации: `resolvePath` по путям плана с проверкой маркеров, маркерный trie (кэш `WeakMap<TemplatePlan, TrieNode>`) — только fallback для случаев, где пути разъехались из-за bare-текстовых дыр. Chromium 14 228 ops/s (0.54x, p50 0.050 мс); на загруженной машине — 0.59x. Trie без path-first был на 8–9% медленнее, поэтому оставлен только страховкой.
- [x] Быстрые пути фиксированных затрат: `findInsertWindow` возвращает окно сразу, если регион начинается с первого ребёнка родителя (типичный `For` в контейнере), `pickSignificantChild` при одном значимом ребёнке берёт `firstChild` без обхода; снимок `innerHTML` для отката убран — повторная попытка идёт полным клиентским рендером (`forceFresh`), а `hydrate` не ждёт уже разрешённый `ready` и не делает лишний `settle`. Chromium 14 228 → 16 269–16 863 ops/s (0.62–0.63x, p50 0.040–0.045 мс). Профиль: GC 26–28%, аллокации — фабрика шаблона 42%, `Set`/`Map` зависимостей 12%, замыкания эффектов 12%.
- [x] Меньше аллокаций: зависимости вычислений хранятся массивами (`deps`/`depVersions` синхронны по индексам, дедупликация `indexOf`) вместо `Set` + `Map`; адоптация шаблона заполняет готовый объект результата (`out`-параметр) без промежуточных `{holes, attrs}`, для пустых `holes`/`attrs` используются общие константы. Chromium 16 854–17 590 ops/s (0.63–0.66x), стартовый JS 26.1 KB / 8.9 gzip.
- [x] Статические выражения шаблона не создают подписок: `renderEffectUnlessStatic` делает пробный проход с лёгким трекером и, если зависимости не прочитаны, оставляет только результат первого выполнения; если зависимости есть — эффект создаётся уже с готовыми `deps` без повторного прогона. Применяется в `text`, `attr` и `textHydrated`. jsdom 1 368 → 1 998 ops/s (0.61x → 0.89x), Chromium 17 371–18 293 ops/s (0.67–0.73x, p50 0.040 мс), стартовый JS 26.8 KB / 9.1 gzip.
- [x] Элемент списка без эффекта для статических детей: `effectUnlessStatic` выполняет `run` в лёгком владельце, при отсутствии зависимостей/вложенных владельцев/cleanup эффект не создаётся; при наличии вложенных подписок они переносятся во владельца созданного эффекта, так что dispose остаётся корректным. Chromium 21 606–23 401 ops/s (0.77–0.87x), jsdom 1 986 (0.88x), стартовый JS 28.0 KB / 9.4 gzip.
